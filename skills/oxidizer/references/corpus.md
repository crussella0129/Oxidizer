# The corpus: building, refreshing, and what is in it

Read this when the corpus is missing, stale, or you need to change what is
mirrored.

## Building

```bash
rustup component add rust-docs                      # ~750MB, one time
python3 skills/oxidizer/scripts/mirror.py --online  # ~30s
```

The offline sources come from `$(rustc --print sysroot)/share/doc/rust/html`.
`--online` additionally fetches the two Brown University sources, which have no
offline equivalent. Skipping `--online` yields a fully functional corpus without
them.

Output goes to `corpus/` at the repository root, or `$OXIDIZER_CORPUS` if set.
It is generated and gitignored — rebuild it, do not commit it.

## Why the local toolchain rather than doc.rust-lang.org

`doc.rust-lang.org` always serves stable-latest. A project pinned to an older
toolchain will disagree with it, silently, in exactly the cases where the user
most needs a correct answer — a method that is not stable yet, a lint that was
renamed, an edition default that changed. Mirroring from the installed toolchain
makes the corpus correct by construction for the compiler that will actually run
the code.

`oxidize manifest` compares the corpus's recorded `rustc --version` against the
current one and reports `STALE` when they differ.

## Selecting sources

```bash
python3 scripts/mirror.py --include core,alloc      # no_std work
python3 scripts/mirror.py --include unstable-book   # nightly features
python3 scripts/mirror.py --only std,lints          # rebuild a subset
python3 scripts/mirror.py --check                   # freshness, writes nothing
```

`--only` merges into the existing manifest rather than replacing it, so
rebuilding one source does not orphan the others.

Defaults on: `book`, `rust-by-example`, `reference`, `nomicon`, `error-index`,
`std`, `cargo`, `clippy`, `edition-guide`, `style-guide`, plus `lints`.
Off by default: `core`, `alloc`, `embedded-book`, `unstable-book` — large, and
std re-exports most of what `core` and `alloc` provide.

## How documents are produced

mdBook pages (`book`, `rust-by-example`, `reference`, `nomicon`, `error-index`,
`cargo`, `edition-guide`, `style-guide`) keep their content in `<main>`; rustdoc
pages (`std`) use `<section id="main-content">` and carry per-member signatures
in `<section id="method.*">` anchors. Both convert to markdown with a stdlib-only
parser — no pip install stands between a user and a working corpus.

For rustdoc pages the extractor also emits a **Members** section: every method's
signature plus its doc block, each as its own heading. That is what lets
`oxidize api Vec::retain` return ~90 tokens instead of the 96,000 the full `Vec`
page costs.

Redirect shims and retired-edition notices are dropped at mirror time. They rank
well on title match while containing no answer, and filtering them at query time
would mean carrying ~750 dead documents.

## The lint index is special

rustup does **not** ship clippy's lint list offline: the clippy book fetches it
with JavaScript at page load, so `share/doc/rust/html/clippy` contains only
clippy's own development documentation. The lint data is instead generated by
running `clippy-driver -W help` (falling back to `rustc -W help`), which
enumerates every lint the installed toolchain knows along with its default
level. This is offline, exactly version-matched, and covers rustc and clippy
lints together — 1,056 entries on a current stable toolchain.

The trade-off: one-line descriptions rather than the full write-ups on
rust-lang.github.io. Enough to identify and act on a lint; for rationale, follow
up in the Book.

## Worked examples: opt-in and not canon

```bash
python3 scripts/mirror.py --algorithms                 # TheAlgorithms/Rust
python3 scripts/mirror.py --algorithms /path/to/repo   # any local Rust checkout
```

This mirrors a repository of Rust *source files* rather than documentation, to
fill a real gap: the canon teaches concepts and documents APIs but contains
almost no complete worked implementations. Each file becomes a document with its
module docs, public signatures, implementation, and tests in separate sections,
so `--section "Public items"` costs ~15 tokens against a ~2,000-token file.

It is **off by default and not canonical**, and that is deliberate — everything
else Oxidizer mirrors is normative or compiler-generated. Indexed at lowest
precedence, and `oxidize manifest` reports `canonical: false` plus the exact
commit each citation is pinned to.

Mirroring also parses the source repo's `[lints.clippy]` table and records which
default-warn style lints it opts out of, so the skill can state the posture the
examples were written under instead of assuming its own. For TheAlgorithms/Rust
that is `needless_range_loop`, `needless_return`, `unwrap_used`, `expect_used`,
`indexing_slicing`, `panic`. Measured against the four style lints in that list
that Oxidizer's own fixtures test for, 9 of its 423 files trip at least one — so
the code is mostly fine, but it is not an idiom authority and must not be
presented as one. See `domains/08_implement/CONTEXT.md`.

The checkout is cached at `corpus/.src/algorithms` and reused on rebuild. Delete
it to force a fresh clone.

## Known gaps

- **crates.io / lib.rs.** Not mirrored. `lib.rs`, named in the project brief, is
  blocked by this environment's egress policy (HTTP 403), and no third-party
  crate documentation is included.
- **Semantic search.** Retrieval is lexical (BM25 plus a curated alias table),
  not embedding-based. A question sharing no vocabulary at all with the document
  that answers it — and not covered by an alias — can still be missed. The
  confidence line reports when that has probably happened.
- **Translated pages.** Rust By Example ships several languages and they are all
  mirrored, so a search can surface a Spanish or Japanese hit. Harmless, but
  check the title before quoting.

## How search works

Retrieval is BM25 over full document bodies, plus a boost for matches in
high-signal fields (title, path, member names, headings). `mirror.py` writes
`POSTINGS.json`, a term-major inverted index — about 34k terms and 713k postings
over 5,657 documents, 6.7 MiB. It is plain JSON so the Python CLI and the Rust
MCP server read it identically, with no database engine and no dependency on
either side.

Two things sit on top of BM25:

- **An alias table** mapping what users say to what the canon calls it
  (`passing` → move/ownership, `'a` → lifetime, `counter` → mutex/arc). This is
  the only fix for questions whose wording shares nothing with the answer: users
  ask about lifetimes precisely because they do not know the word "lifetime".
  Expansions are scored at a discount so they widen recall without overriding
  the user's own terms.
- **A confidence line** reporting how many of the question's terms the top
  result actually contains. Raw scores are not comparable across queries or
  source filters and are useless for this — before the rewrite, a wrong answer
  scored 58 while a right one scored 27.

Measured on a 13-question benchmark of naturally-phrased questions
(`tests/run_tests.py`, section 12):

| | before | after |
|---|---|---|
| precision@1 | 0% | 62% |
| recall@5 | 10% | 100% |

The benchmark accepts any of several correct documents per question, since the
Book chapter and the corresponding std page are often both right answers.

## Size

With `--online` and `--algorithms`, 5,657 documents and ~8.6M tokens:

| | |
|---|---|
| markdown | 34.1 MiB |
| `INDEX.json` (per source) | 4.6 MiB |
| `POSTINGS.json` (full-text index) | 6.7 MiB |
| **total** | **47.9 MiB** |

Distilled from 750 MiB of shipped HTML. (`du` reports more, counting allocated
blocks across 5,657 small files.) Small enough to keep several corpora around
for different toolchains, and dwarfed by any Rust `target/` directory — see
`disk-hygiene.md`, and `oxidize disk` for current numbers.
